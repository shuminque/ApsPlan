# 当前排产逻辑说明（用于部门研讨）

本文基于当前代码实现，对“排产预览/提交”这一套 APS 逻辑做可讨论版本的拆解说明。

## 1. 入口与流程总览

- 前端通过 `POST /api/shift/plan/preview` 触发排产预览，控制器调用 `ProductionPlanningService.generatePlanPreview(start, end)`。  
- 预览返回包含三类数据：
  - `events`：用于日历展示的排产块；
  - `orders`：按客户/内外圈/型号聚合后的订单需求预览；
  - `dailyOutputs`：按天、按产线的明细产量。
- 前端通过 `POST /api/shift/plan/commit` 提交选中的预览事件（或会话缓存中的预览事件）并落库。

> 讨论重点：当前“算法计算”在 `ProductionPlanningServiceImpl`，`ShiftCalendarController` 主要负责请求路由与预览缓存。

## 2. 预览排产主流程（generatePlanPreview）

### 2.1 时间窗口处理

1. 将传入字符串转 `LocalDate`（仅截取前 10 位 `yyyy-MM-dd`）。
2. 若开始/结束任一为空，直接返回空预览。
3. 实际排产开始日 `start` 不允许早于今天（过去日期会被抬到今天）。
4. 若 `start >= endExclusive`，则把结束日改为 `start + 1个月`。

**影响**：即使前端给了过去日期或非法区间，也会被“纠偏”为可计算区间。

### 2.2 订单筛选

- 仅取“开放状态”订单（状态枚举在 `ProductionOrderStatus.openStatusFilterValues()` 定义）。
- 同时要求 `quantity > 0`。
- 若无开放订单，直接返回空预览。

### 2.3 基础数据装配（安全库存、订单分组、在库）

- 拉取全部安全库存，按 `customer|outerInnerRing|model` 建键值索引。
- 将开放订单按相同键进行分组。
- 调用 `queryCurrentInventoryByKey(start, orderByKey)` 查询“排产开始日截止（含当日）净在库”，作为需求净额计算口径。

> 口径在代码有明确注释：在库用于“需求净额”和“前端在库展示”保持一致。

### 2.4 需求净额计算（buildDemands）

按每个 `customer+内外圈+型号` 组计算：

- `orderQty = Σ max(0, quantity - assignedQuantity)`
  - 即未分配订单量；
- `safetyTargetQty = round(stockCycle * monthlyStockQty)`（四舍五入）；
- `required = max(0, orderQty - currentInventory + safetyTargetQty)`。

若 `required <= 0` 则该组不参与排产。

同时记录该组最早交期 `earliestDelivery` 用于优先级排序。

### 2.5 需求优先级排序

需求列表排序规则：

1. 先按交期紧迫度（`earliestDelivery - today` 天数）升序；
2. 再按 `required` 降序。

即“越急越先排；同紧急度下数量越大越先排”。

### 2.6 自动扩展结束日期

- 取需求中“最晚最早交期”的次日作为 `latestDeliveryExclusive`。
- 若用户传入的 `endExclusive` 早于该日期，则自动延长到该日期。

**目的**：避免排程窗口太短，导致后续交期的需求永远看不到排程结果。

### 2.7 班次工时（日可用工时）

对 `start ~ endExclusive` 每天计算：

- 从 `ShiftCalendarService.getSchedulesByDate(day)` 拉班次；
- 将当日所有班次时长累加为小时数；
- 若计算结果 <= 0，则回退默认 `8` 小时。

班次时长计算规则：

- 以 `endDateTime - startDateTime` 的分钟差计算；
- 若分钟差 <=0 且结束日期跨天，则按 24h 处理；
- 仍 <=0 则记 0。

### 2.8 产线产能模型（buildModelCapacities）

- 读取产线型号配置与产线主数据；
- 过滤：停用配置（`status == 0`）、型号为空、小时产能为空、产线ID为空；
- 组装 `model -> [lineCapacity...]` 映射；
- 每组按 `priority`（空值最后）再按 `lineId` 升序排序。

### 2.9 型号匹配策略（findMatchingLines）

对某需求型号 `demandModel`：

1. 先查**完全匹配**配置型号；命中后直接用该集合。
2. 完全匹配无结果时，做**系列前缀匹配**：`demandModel.startsWith(configModel)`。
3. 返回匹配到的产线列表（按优先级/线体ID排序）。

### 2.10 日滚动分配（核心分配循环）

算法是“按天推进、按需求顺序、按可用产线顺序分配”：

- 外层：`day = start -> endExclusive-1`。
- 中层：遍历排序后的 `demands`。
- 内层：遍历该需求可匹配产线 `lines`。

每条需求在某天某线分配量：

- 先用 `remainingCapacityByLineDay(line, day)` 维护“线-日剩余产能”
- `assignQty = min(remainingCapacityByLineDay, demand.remaining)`
- `remaining -= assignQty`
- `remainingCapacityByLineDay -= assignQty`
- 记录计划切片 `PlanSlice(day, line, customer, outerInnerRing, model, assignQty)`。

此外，当前实现新增了**最少产线启用**策略（`LineActivationPlan`）：

- 对同一激活键（客户/内外圈/型号，或 LA/LB 配对键）先按“未来剩余产能”排序候选线；
- 仅激活满足该需求所需的最小线集合，优先减少并行启线数量；
- 若当天激活线都无剩余产能，再回退到当日有余量的候选线。

> 结论：同线同天已做容量互斥扣减，且存在“最少启线”倾向；但其目标函数仍偏启线数量最小化，不等于全局最优（如最短延期/最少换型）。

### 2.11 结果组装

- `events`：将连续天、同一 `line+customer+内外圈+model` 的切片合并成一个日历块，标题格式为：
  `[排产] 线体 客户/内外圈 型号 x 数量`
- `orders`：输出每组需求的
  - 在库、需求量、已排量（`required - remaining`）、已排天数；
- `dailyOutputs`：保留逐日逐线明细。

## 3. 计划提交（commit）机制

- 预览接口会把 `events` 缓存在 `sessionId -> events`。
- 提交接口优先用前端显式传入 `selectedEvents`；若为空则用会话缓存。
- 提交后会清理该会话缓存。

## 4. 当前逻辑特点（可直接用于会议讨论）

### 4.1 优点

- 简单直观、可解释性强，易落地。
- 通过“交期+需求量”排序，兼顾紧急与体量。
- 支持“型号精确匹配 + 系列前缀兜底”，减少无产线可排的情况。
- 班次工时参与日产能计算，较固定日产能更贴近现场。

### 4.2 局限/风险

1. **最少启线是局部启发式**：按需求键逐步激活线体，不保证全局最优（延期、换型、均衡）。
2. **未考虑换型损失/切换成本**：同线跨型号切换无惩罚。
3. **未考虑订单级拆分约束**：当前在订单+安全库存混合需求维度排程，不保证单订单粒度最优。
4. **未考虑设备状态/停机因素**：运行状态数据未进入排产约束。
5. **预览到提交基于事件文本**：如果后续需要追溯订单级分配，事件粒度可能不够。

## 5. 研讨建议（下一步可选）

- 将“最少启线”从局部规则升级为可配置目标（如“延期优先/启线优先/换型优先”多目标权重）。
- 增加“切换损耗模型”（同线跨系列/跨型号损失工时）。
- 把 `DemandItem` 从“组维度”细化到“订单维度+组维度混合”，兼顾可解释与可交付。
- 将 `ProductionLineRuntime`（停机、效率等）并入日产能。
- 形成“预览ID + 明细表”提交机制，提升可追溯性。
